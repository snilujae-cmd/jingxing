# 景行智调：更新部署与回退说明

本说明供仓库与 Streamlit Cloud 账号持有人操作。本次交付完成本地源码准备与测试，未推送 GitHub，也未更新公网版本。正式合并和发布应在项目负责人审阅完整源码包、文件清单及本次验收报告并确认之后进行。

## 1. 更新前固定稳定版本

请先在 [GitHub 仓库](https://github.com/snilujae-cmd/jingxing) 选择当前 `main`，打开最近一次提交，复制该提交的完整 40 位 SHA、页面链接和日期，写入团队自己的发布记录。通过该固定提交的文件浏览页面下载源码 ZIP，命名为“稳定版_日期_提交号.zip”，保存在交付目录以外。若会使用 Git，也可由整合负责人建立备份分支或标签指向此提交。

同时保留目前本地稳定项目副本，记录是否还有未提交的更改，先由各文件负责人确认保留方式。不要只备份入口或 User 页面；核心模块、数据、配置和依赖需要一起保留。

由 Cloud 账号持有人记录应用地址、仓库、分支、入口路径、Python 版本和最后部署日志中能确认的提交。Secrets 继续保存在原 Cloud 配置中；如需团队备份，由账号持有人使用原有安全保管方式处理。不要把 Secrets、真实管理员密码、令牌或包含这些内容的截图放入本次文件包、GitHub 或聊天。

如远端已包含相同修复，可在差异清单上标记“已存在”。如同一文件两边都有新改动，应由负责人合并需要保留的部分，并重新测试；不要直接用交付包覆盖整个远端工作目录。

## 3. 在独立分支整合

推荐使用 GitHub Desktop：先确认现有未提交改动已备份，或已提交到它们原来的工作分支；在“Current branch”选择 `main`，点击“Fetch origin”，如随后出现“Pull origin”则点击拉取。确认本地 `main` 已更新到第一步记录的最新远端提交，再创建本次视觉整合分支，例如 `feature/visual-b-integration`。界面应显示该分支后，再复制和合并文件。

将 ZIP 解压到一个新目录。源码包根目录中的 `app.py` 对应仓库根目录 `app.py`；`assets/`、`views/`、`utils/`、`core/`、`data/` 及 `.streamlit/` 保留各自层级。不要额外套入一层交付目录，也不要把 ZIP 作为仓库里唯一新增文件。

根据逐文件清单处理“新增 / 修改 / 删除”。新增图片资源和 `comparison_data.py` 需要与引用它们的页面一起整合。对修改文件使用 GitHub Desktop 的差异视图逐个确认，特别检查：

- `app.py`：游客仍是默认入口，Admin 页仍受原验证保护。
- `views/user.py`、全部 Admin 页面：保留远端新功能，再合入布局、图片及比较展示。
- `shared_run_store.py`、`comparison_data.py`：成组加入，保留原单次 API 和四 CSV 契约。
- `utils/style.py`、`utils/media.py`、`assets/`：同步加入；图片按相对路径引用。
- `requirements.txt`、`.streamlit/config.toml`：与交付清单核对；本次未新增运行依赖。
- `admin_auth.py`、`user_data_adapter.py`、`core/`、既有数据 CSV：与已确认基线对照；本次视觉与 B 方案不要求重写这些内容。

确认未选入 `.git`、`.venv`、`__pycache__`、测试临时目录、运行时 `data/shared/`、`.streamlit/secrets.toml` 或其他私有配置。在整合分支运行本地测试并完成浏览器验收后，填写本次验收记录。未经负责人确认，保持本地分支即可。

## 4. 获准后提交与审阅

负责人确认允许更新 GitHub 后，在 GitHub Desktop 再次检查“Changes”的每个文件，提交到整合分支并发布该分支。提交说明应写明“视觉与素材集成、三策略比较只读发布层”，不要写“重写仿真算法”。

在 GitHub 创建 Pull Request，目标为 `main`，附本次逐文件清单、测试结果、已知未验证项及回退 SHA。由团队审阅具体差异。若主分支又更新，应先保留其他同学改动并重新完成受影响的检查，再请求合并确认。

若现有 Cloud 应用跟踪 `main`，合并此 PR 就可能触发公网更新，因此合并前必须取得正式发布确认。Cloud 会随其所跟踪分支的源代码变化更新应用，依赖变更也会重新处理。此行为见 [Streamlit 官方部署说明](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/deploy)。

## 6. 公网重新验收

以下项目应在更新后的公网应用重新执行，逐项填“通过 / 失败 / 未验证”，附时间、浏览器及必要截图。不要复制本地测试的结论作为公网结果。

1. 新无痕游客默认进入 User；首页照片、地图原图查看、线路查询和手机窄屏正常。
2. 未登录直接打开 Admin 地址受阻；错误密码受阻；正确登录后七个主要管理页均可打开；退出后再次直接访问受阻。
3. 保存客流场景，到调度页核对读取值；运行单次策略，记录运行编号并导出原四 CSV。
4. 运行同场景三策略，记录比较编号、随机种子、客流签名和三条运行编号；独立游客刷新后核对全部关键指标一致。
5. User 回放、队列、车辆状态、趋势分析和共享刷新工作正常，且没有后台操作入口。
6. 再发布单次运行，游客刷新后不再附带上一组三策略结果。
7. 图片缺失降级检查可在本地验收副本执行；公网检查实际图片全部可读、比例正常、线路图文字可辨，不要临时删改正式应用素材。
8. 所有页面保留科研情景仿真说明，没有将数据表述为景区真实实时车辆或官方排队信息。

图片来自用户提供的素材包，来源及授权状态见 `assets/manifest.json`。正式公开前由团队确认使用许可，保留水印和必要署名。

## 7. 共享结果的存储边界

默认共享位置为应用运行实例的 `data/shared/current_run.zip`，采用原子替换保证单次四 CSV 与比较元数据来自同一包。运行单次策略会整体替换它，并移除上一组比较。该文件由 Admin 运行成功后生成，属于运行数据，不放进源码 ZIP 或 GitHub。

此本地路径服务于同一服务器实例的跨浏览器读取。Cloud 重启、休眠恢复或实例变更后，不保证运行文件长期保留。正式演示前由管理员重新生成并发布，再用独立游客核对编号。多实例或长期历史保存需要团队后续配置统一持久存储；单纯设置环境变量 `JINGXING_SHARED_RUN_PATH` 并不会自动提供持久存储。本轮没有新增数据库或外部对象存储。

## 8. 故障回退

先记录故障页面、报错、部署提交和时间，保留本次源码 ZIP及报告。不要把新的仿真结果覆盖到稳定版备份中。

若本次更新通过 PR 合并，优先由仓库负责人在该已合并 PR 中使用 GitHub 的 Revert 操作创建回退 PR；审阅并合并后，`main` 会新增一个撤销本次改动的提交，保留已有历史，参见 [GitHub 官方回退说明](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/reverting-a-pull-request)。若 Revert 无法自动执行，让负责 Git 的同学依据更新前固定的 SHA 创建回退分支并逐文件恢复，再通过 PR 审阅。不要对共享 `main` 强制推送、删除历史或清除他人提交。

如果更新后还有其他同学提交，回退应撤销本次发布对应的改动并保留后续独立工作；发生同文件冲突时交由文件负责人处理。恢复时使用固定稳定提交或稳定 ZIP，避免凭记忆拼回个别文件。

Cloud 重新部署回退后的代码时，保持原仓库、分支、入口和 Secrets，确认部署日志对应回退提交，再重复游客首页、管理员登录退出、单次仿真与共享读取的最小验收。回退后的运行时共享文件可能缺失或仍含新版比较条目；由管理员用回退代码重新运行并发布单次结果，再让游客刷新核对。记录回退完成时间与实际验证结果。
